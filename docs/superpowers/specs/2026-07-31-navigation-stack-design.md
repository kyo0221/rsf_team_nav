# Navigation stack design (rsf_navigation_executor)

## Goal

Add Nav2-based navigation to the RSF robot, using `emcl2` for localization instead of
`amcl`, buildable from source alongside a from-source Navigation2, and runnable end to
end in the existing Ignition Gazebo simulator (`tsudanuma2-3` world).

## Repositories

New `rsf_ws/src/navigation.repos` (same format as the existing `deployment.repos`):

```yaml
repositories:
  navigation2:
    type: git
    url: https://github.com/ros-navigation/navigation2.git
    version: humble
  emcl2_ros2:
    type: git
    url: https://github.com/CIT-Autonomous-Robot-Lab/emcl2_ros2.git
    version: main
```

`humble` branch is required because the workspace underlay is ROS 2 Humble; `main` is
the only branch of `emcl2_ros2` and already supports Humble. Installed via
`vcs import src < src/navigation.repos`.

## New package: `rsf_navigation_executor`

Follows the existing `rsf_bringup` / `rsf_description` / `rsf_simulator` layout
(`package.xml`, `CMakeLists.txt` using plain `ament_cmake`, `config/`, `launch/`).
No custom nodes are needed, so `CMakeLists.txt` only installs directories, matching
`rsf_simulator`'s pattern.

```
rsf_navigation_executor/
├── package.xml
├── CMakeLists.txt
├── config/
│   ├── nav2_params.yaml
│   ├── emcl2_params.yaml
│   ├── pointcloud_to_laserscan_params.yaml
│   └── slam_toolbox_params.yaml
├── maps/
│   └── tsudanuma2-3.yaml / .pgm   (generated by SLAM, see below)
└── launch/
    ├── navigation.launch.py       (normal bring-up entry point)
    └── slam.launch.py             (one-off map-building utility)
```

## TF / topic facts driving the config

- TF chain (existing): `rsf_odom` -> `base_footprint` -> `base_link` -> `rsf_x001_link`
  -> `rsf_hokuyo3d` (published by `tf_odom_to_footprint` + `robot_state_publisher`).
- Odometry topic: `/rsf/rsf_odom` (`nav_msgs/Odometry`).
- Only a 3D point cloud sensor exists (`/rsf/hokuyo_cloud2`, `sensor_msgs/PointCloud2`),
  no native `LaserScan`. `pointcloud_to_laserscan` (apt package, no source build needed)
  converts it to `/scan` for both the costmap obstacle layer and `emcl2`.
- No map exists for `tsudanuma2-3` yet; one is generated with `slam_toolbox` (apt
  package) as part of this work and committed under `rsf_navigation_executor/maps/`.

## Node graph (launch/navigation.launch.py)

1. `pointcloud_to_laserscan` node: `/rsf/hokuyo_cloud2` -> `/scan`.
2. Localization group (custom, since `nav2_bringup`'s `localization_launch.py` is
   `amcl`-specific):
   - `nav2_map_server/map_server` loading the `map` launch argument (default: the
     committed `tsudanuma2-3.yaml`).
   - `emcl2/emcl2_node` (`odom_frame_id=rsf_odom`, `footprint_frame_id=base_footprint`,
     `base_frame_id=base_link`, `global_frame_id=map`, scan on `/scan`).
   - `nav2_lifecycle_manager/lifecycle_manager` managing `['map_server']` only —
     `emcl2_node` is a plain `rclcpp::Node`, not lifecycle-managed.
3. Navigation group: `nav2_bringup`'s `navigation_launch.py` included via
   `IncludeLaunchDescription`, passed `params_file=nav2_params.yaml`, `use_sim_time`,
   `autostart`. This reuses upstream's node wiring (controller/planner/behavior server,
   bt_navigator, waypoint_follower, velocity_smoother, lifecycle_manager_navigation)
   instead of re-declaring every node, consistent with how `rsf_bringup` already
   includes `icart_driver`'s launch file.

`nav2_params.yaml` uses `nav2_mppi_controller::MPPIController` for the controller
server and `nav2_smac_planner::SmacPlanner2D` for the planner server (both chosen over
DWB/NavFn), with `robot_base_frame: base_footprint`, `odom_topic: /rsf/rsf_odom`, and
costmaps sourcing obstacles from `/scan`.

## Map generation (one-off, not a repo feature)

1. Launch `rsf_simulator` + `rsf_bringup` (`sim:=true`).
2. Launch `rsf_navigation_executor`'s `slam.launch.py` (`slam_toolbox`, online async,
   same frame/topic conventions as above).
3. Drive the robot around the world via a throwaway `cmd_vel` script (not committed).
4. Save the result with `map_saver_cli` into `rsf_navigation_executor/maps/`.

## Verification (no display available for RViz, so CLI-driven)

- `colcon build` succeeds for `navigation2`, `emcl2`, and `rsf_navigation_executor`.
- After `navigation.launch.py`, all managed lifecycle nodes reach `active`.
- Publishing `/initialpose` converges `/mcl_pose`.
- A `NavigateToPose` action goal sent via `ros2 action send_goal` returns `SUCCEEDED`
  and `/rsf/rsf_odom` shows the robot actually moved.

## Explicitly out of scope

- Real-robot (`sim:=false`) tuning of the navigation parameters.
- Any controller/planner other than MPPI + SmacPlanner2D.
- A permanent/automated mapping pipeline — the map is generated once and committed.
